# 変更後の不要コード整理

リポジトリの指示、公開API・互換性の方針、コードの所有範囲、既存の静的解析・検証を優先する。今回の変更で不要になったものを整理し、無関係なリファクタリングへ広げない。

## 整理する対象

1. **置き換えた旧経路**: 対象diffから旧module・symbol・入口を拾い、`rg`、言語の参照検索、既存の未使用コード検査で利用元を確認する。実装だけでなく、テスト、script、CI、設定、ドキュメントからの参照も調べる。
2. **静的検索に現れない利用元**: packageのexports、公開API、plugin登録、動的import、文字列による登録、frameworkの規約による入口、生成処理、外部利用者を確認する。単に検索結果が0件という理由で削除しない。外部利用が不明な公開物は候補として報告する。
3. **残った互換層・再export**: 参照が不要になった旧pathや転送を整理する。公開APIや段階移行のために必要な互換層・barrel exportは、利用側の契約に従って保持する。
4. **重複した処理**: 新しいhelperを書く前に既存の同等処理と正本を探す。共有が必要なら、読み手の都合で同じ型や処理を再宣言せず、責務に合う既存の共有moduleを使う。似た式だけを根拠に、業務の意味が異なる処理を統合しない。
5. **連鎖して不要になった依存・設定**: 部品・script・依存の最後の利用元を消した場合、manifest、lock、設定、起動登録、関連する生成手順を確認する。依存とlockは利用側のpackage managerで更新する。

## 変更の進め方

- 削除・統合の根拠を確認してから、担当範囲の旧実装・不要参照を同じタスクで整理する。利用者や別作業の差分を消さない。
- 移動・重複排除では、戻り値、例外、終了コード、保存形式、時刻・単位など、既存の振る舞いを保持する。契約変更が必要なら、単なる整理として混ぜず依頼範囲と照合する。
- 生成物やhashで固定された資材は手編集せず、利用側の更新手順を使う。拒否処理、権限チェック、回帰テストは、現行の契約を守る役割が残っていないか確認する。
- 文書やコマンドの名前に影響したら、関連するREADME・仕様・参照も同期する。`project-docs-sync` が利用可能なら、その手順を使う。

## 検証と報告

1. 整理後に旧symbol・path・依存の参照を再検索し、必要な利用元が切れていないか確認する。
2. 利用側の未使用コード・依存の検査、変更箇所に対応する型検査・試験・lintを実行する。公開exportや起動入口を変えた場合は、それを読む側・起動する側の検証も含める。
3. 削除・統合したものとその根拠、互換性のために保持したもの、検証結果、未確認の利用元を報告する。

調査だけの依頼では編集せず、各候補に根拠のpath・symbolと利用状況、振る舞いや互換性への影響を添える。外部リソースの削除はコード整理に含めない。
